# Работа агента

## Взять задачу

1. Прочитайте поручение и ту же карточку в [Notion](https://app.notion.com/p/41da64edce32819e82add67138cf52bd?pvs=204). В карточке зафиксируйте границы, критерий готовности, текущий `Цикл`, имя или ссылку на чат одного ответственного агента и связанные документы. Для новой карточки цикл начинается с 1. Свободные карточки остаются без назначения до начала работы.
2. Выберите документы по затронутому модулю из [быстрого старта](../README.md). История нужна для конкретного решения или расхождения. Зафиксированные факты исходной папки доступны в `project-hub/LOCAL_SYSTEM_HANDOFF.md`, UI-эталон — в `design/demo/index.html`.
3. Работайте в отдельном `git worktree` под веткой `codex/<задача>`. Основа для серверного кода — актуальный `origin/main`. У каждой параллельной задачи собственные конфигурация, порты, БД, сессии, логи и процессы. БД создаётся из синтетических данных. [Команды и проверки](LOCAL_QA.md).
4. При изменении UI до правки откройте [Витрину](../app/local-admin/VITRINE.md) и используйте её компоненты. Новый компонент и пример проверяются в той же задаче. В PR и карточке обязательны ссылка на пример и итог браузерной сверки перед выкладкой.

## Изменение и документация

- Вместе с кодом в том же PR обновите относящийся к нему документ. Команды запуска и тестов — в [локальной проверке](LOCAL_QA.md), маршруты и контракты данных — в [технической карте](ARCHITECTURE.md), UI — в [Витрине](../app/local-admin/VITRINE.md), путь на сервер — в [автодеплое](AUTODEPLOY.md).
- В Notion ведите задачи, подтверждённые решения, открытые вопросы и ссылки на конкретные файлы в Git. Для решения запишите, что принято, кто подтвердил, дату или ссылку на основание и где правило действует. Предложения оставляйте вопросами до подтверждения.
- В карточке оставьте результат проверок для текущей версии и окружения. При продолжении используйте проверку того же кода, данных и окружения. Если изменился контракт или среда, перепроверьте затронутый сценарий. Широкий набор нужен при интеграции и по фактическому риску задачи.
- Откройте PR в закрытом серверном репозитории. До команды «выкладывай» PR может пройти проверку в рабочей ветке. Текущий workflow автоматически запускается на push в `main`. Для ветки есть ручной `workflow_dispatch` с явным `--ref`. Job выкладки для неё пропускается. Самостоятельный запуск на ветке `main` тоже выкладывает. [Workflow](../.github/workflows/check.yml).

## Выкладка и закрытие

У карточки два статуса — **Открыта** и **Закрыта**. Очередь и технические стадии отражаются в GitHub Actions. Одна карточка сопровождает изменение от поручения до результата.

1. Получив «выкладывай» для этой задачи, ответственный агент сверяет актуальность ветки и проверки, позицию в очереди текущих job и условия PR. Применяет штатное слияние в `main` и находит запуск точного SHA. Если в очереди другой релиз, сверяет результат своего запуска и фактический SHA на сайте. Устаревший или пропущенный запуск сам по себе карточку не закрывает.
2. Дождитесь успешных `check` и `deploy` в GitHub, затем проверьте health, публичный SHA и изменённое поведение на сайте. UI-правку проверьте в браузере. При ошибке или откате оставьте карточку открытой и зафиксируйте проверяемый результат. [Команды и условия](AUTODEPLOY.md#цикл-агента).
3. Перед сменой статуса прочитайте карточку снова. Приложите PR или запуск выкладки, SHA и короткий итог проверки для текущего цикла. Закройте её сами. Задачу без выкладки закройте по проверенному результату, приложив PR или другой проверяемый результат.
4. Чтобы открыть задачу повторно, владелец меняет статус на **Открыта**, отмечает причину и начинает следующий цикл в той же карточке. Предыдущая проверка остаётся в истории, а поле активной ссылки обновляется только после повторной проверки. Если владелец поменял только статус, агент переносит прежнюю ссылку в историю и увеличивает цикл перед новой работой. Успех старого PR или Actions run к новому циклу неприменим. Закрывать карточку нужно только по новому доказательству исправления, проверенному после повторного открытия.
